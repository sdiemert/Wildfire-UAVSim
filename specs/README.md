# Policy requirements specifications

This directory holds a requirements specification for each UAV policy in `sim/policy/`, written so that
three things can be linked and kept linked: what the policy is required to do, the code that does it, and
the tests that show it does.

That link is the point. Anyone can read `sim/policy/firefighter.py` and see what it does now; what this
directory adds is the ability to answer *which tests demonstrate that the firefighter policy honours the
fuel reserve*, and to be told when the answer becomes "none".

## Layout

```
specs/
  README.md          this file: the authoring contract
  TRACEABILITY.md    generated by `python3 tools/trace.py report` -- do not edit by hand
  policies/
    _contract.md     POL-GEN-*  obligations binding every policy
    random.md        POL-RND-*
    follow-fire.md   POL-FOL-*
    defend-base.md   POL-DEF-*
    disperse.md      POL-DSP-*
    firefighter.md   POL-FF-*
```

## The three legs of the trace

Each leg has exactly one source of truth, and each is machine-checked, so none of them can rot quietly.

| Leg | Lives in | Checked by |
|-----|----------|------------|
| Requirement | the statement blockquote in `policies/<name>.md` | anatomy and schema validation |
| Implementation | that requirement's `satisfied_by:` | AST resolution of `path::Symbol.method` |
| Verification | `@pytest.mark.verifies("POL-FF-1")` on the test | AST scan of `tests/` |

Note which direction the verification link runs. Tests are **not** listed in the spec; the test names the
requirement. A test that is renamed or moved carries its marker with it, whereas a list of test node IDs
in a spec file would go stale the first time anyone reorganised a test module and nothing would notice.

`tests/test_traceability.py` fails the suite on a broken link, so the trace is maintained by the same
mechanism that maintains everything else here.

## Requirement records

A requirement has five parts, in this order. Two are required; the rest are there when they earn their
place.

1. a `## <ID> — <short title>` heading;
2. an optional **preamble** — plain text, for the context a reader needs before the obligation makes
   sense;
3. **the statement**, as a Markdown blockquote. Required, and exactly one per requirement;
4. optional **rationale and discussion** — plain text: why the requirement exists, worked examples, the
   history behind a decision, notes on what is deliberately *not* required, and the assumptions it rests
   on;
5. a **YAML block**, last, holding metadata and traceability and nothing else.

````markdown
## POL-FF-1 — The fuel reserve outranks everything else

The first rung of the ladder, checked before the water the UAV carries and before anything burning in
view.

> When `observation.low_fuel()` is true, the policy SHALL fly the UAV toward `observation.base_pos` and
> SHALL NOT select a fire as its target, whatever water it carries and whatever is burning in view.

A UAV that runs dry loses every health point it has. Losing the airframe costs the rest of the run more
than the one water drop that pressing on would have delivered.

**Assumptions:**

- `config.ACTIVATE_FUEL` is true. With the extension off, `observation.low_fuel()` is never true and this
  rung of the ladder never fires.
- `config.UAV_FUEL_RESERVE` is a flat share of the tank rather than an estimate of the fuel needed to
  reach the base, so a UAV that has strayed far enough can still run dry on the way home.

```yaml
id: POL-FF-1
satisfied_by:
  - sim/policy/firefighter.py::FirefighterPolicy.action_for
  - sim/policy/observation.py::Observation.low_fuel
verified_by: test
status: agreed
```
````

The statement is a blockquote so that it reads as *the obligation* rather than as one field among several,
and so that Markdown works inside it: `observation.low_fuel()` and `UAV_FUEL_RESERVE` should look like
code, which they cannot do inside a YAML scalar. It stays machine-readable regardless — it is the one
blockquote between the heading and the YAML block, and `tools/trace.py` enforces exactly that.

The anatomy is checked, and every rule is a way the layout could drift back into burying the statement:

- exactly one blockquote in the section;
- the blockquote comes before the YAML block;
- exactly one YAML block, with nothing after it;
- the statement says `SHALL`.

**Assumptions** are prose, under a `**Assumptions:**` lead-in. That is a convention rather than a checked
rule, so keep to it: they are the conditions a requirement holds under and the first place a reviewer
looks for a defeater, and they are worth being able to find by eye in every file.

### Fields

The YAML block is four fields and nothing else. Anything a human writes at length belongs above it, and
the parser rejects a folded scalar (`key: >`) rather than letting prose creep back in.

| Field | Required | Meaning |
|-------|----------|---------|
| `id` | yes | `POL-<TAG>-<n>`. Unique across all specs, and `<TAG>` must match the file it appears in. Must match the heading. |
| `satisfied_by` | yes | List of `path::Symbol` or `path::Symbol.method`, each of which must resolve. |
| `verified_by` | yes | `test`, `inspection`, `analysis`, or `none`. |
| `status` | yes | `draft`, `agreed`, or `retired`. |

`verified_by: test` is the normal case and obliges at least one tagged test to exist. The other three
values are escape hatches that stay visible: `inspection` and `analysis` record that the evidence is
human judgement rather than a test, and `none` records a gap on purpose. All three are counted in the gap
summary of `TRACEABILITY.md` rather than being silently accepted.

`status: retired` keeps a requirement in the file, and its ID out of circulation, once it no longer
applies. Retired requirements are not checked for verification. Deleting a requirement outright is wrong:
it frees the ID for reuse, and an ID that means two different things across the history of the repository
makes every past review unreadable.

### The ID scheme

`POL-<TAG>-<n>` with tags `GEN`, `RND`, `FOL`, `FF`, `DEF`, `DSP`.

`<n>` is opaque. Allocate the next unused number in the file and never renumber, not to close a gap left
by a retirement and not to put the requirements in a nicer order. The heading order in the file is what
controls presentation; the number is an identity.

## Writing a requirement Claude Code can act on

The specifications are meant to be handed to Claude Code as the thing to implement and test against, so
they have to be precise enough to be executable by a careful reader who has not seen the code. Seven rules
get most of the way there.

**One obligation per requirement.** If a statement needs "and" between two behaviours, it is two
requirements. A test can only pass or fail as a whole, so a requirement covering two behaviours produces
evidence that cannot say which of them held.

**Use `SHALL`, and say when.** Every statement takes the form *when \<observable condition\>, the policy
SHALL \<observable action\>*. Both halves have to be there. "The policy SHALL prioritise buildings" names
no condition and no action, and two people will implement it differently; "when the observation contains
a burning cell within `WATER_DROP_RADIUS` of a cell in `observation.building_positions`, the policy SHALL
select that cell as the target in preference to any other burning cell" can be turned into a test without
asking anyone a question.

**Speak the public interface.** State requirements over `Observation` fields going in and `Action` values
coming out — the vocabulary in `sim/policy/observation.py` and `sim/policy/action.py`. Do not state them
over private helpers. `satisfied_by` may point at a helper, because that is a trace to where the work
happens, but a statement written in terms of `pick_target()` becomes false the moment somebody renames it,
which is exactly the refactoring a specification is supposed to survive.

**Name the config knob, not the number.** Write `UAV_FUEL_RESERVE`, not `0.25`. Every module here reads
its settings through `config.` at the point of use precisely so a run can override them, and a
requirement pinned to today's default would be violated by a legitimate configuration.

**Specify precedence separately.** `firefighter` and `defend-base` are ordered ladders of rules: fuel
first, then water, then fire, then buildings. Each rung is its own requirement, *and* there is one further
requirement asserting the ordering itself, verified by a test that constructs an observation satisfying
two rungs at once and checks which one wins. Precedence is the part a refactor breaks most easily and the
part that the individual rung requirements, each tested in isolation, cannot catch.

**Record the assumption instead of ducking it.** Most policy behaviour is conditional on
`ACTIVATE_FIREFIGHTING` or `ACTIVATE_FUEL`, and some of it rests on `UAV_SPEED` being no larger than
`UAV_OBSERVATION_RADIUS`. Put those under `**Assumptions:**` rather than narrowing the statement until
they disappear. An assumption written down can be reviewed and challenged; one that has been absorbed into
the wording of a requirement cannot.

**Justify it, even though nothing makes you.** The rationale is prose now, and unchecked — the format
cannot tell a paragraph of justification from a paragraph of anything else. Write it anyway. A statement
with no recorded reason is a claim nobody can review: the next person cannot tell whether it is load
bearing or left over, and an assurance argument has nothing to cite for why this is the right obligation
to be making.

## Tagging a test

```python
@pytest.mark.verifies("POL-FF-4")
def test_a_uav_down_to_the_reserve_breaks_off_for_home(policy, observation):
```

A test may verify several requirements — `@pytest.mark.verifies("POL-GEN-1", "POL-GEN-2")` — and several
tests may verify one. The marker is registered in `pyproject.toml`, so `pytest -m verifies` collects the
tagged subset.

Only string literals are read. A marker built from a variable is reported as an error rather than being
skipped, because a link the tool cannot follow is worse than no link at all.

Tag the test that actually demonstrates the requirement. A test that touches the behaviour incidentally
on the way to checking something else is not evidence for it, and tagging it produces a trace that looks
complete and is not.

Tag a test in a per-policy file with a `POL-GEN-` id only when it adds evidence the parametrised contract
suite does not already have. `tests/policy/test_follow_fire_policy.py::test_returns_one_action_per_uav_in_order`
is tagged `POL-GEN-1` because the contract suite checks the length of the returned list and not its order;
`tests/policy/test_random_policy.py::test_returns_one_action_per_uav` is not tagged, because it repeats
what the contract suite already covers for every policy at once. Redundant links are not wrong, they are
just noise in a document whose whole value is being read.

## Working on a policy

1. Read `policies/<name>.md` before changing the policy.
2. Changing behaviour means amending or adding a requirement **first**. The specification leads the code.
3. A new requirement needs `satisfied_by` and at least one test tagged with its ID.
4. Run `python3 tools/trace.py check` before calling the work done, and `python3 tools/trace.py report`
   if anything about the trace changed.
5. Never renumber an ID. Retire it with `status: retired`.

Adding a whole new policy additionally means writing `policies/<my-policy>.md`, named after the policy's
registered `name`, with a tag no other file uses. There is nothing to register in `tools/trace.py`: it
reads `sim.policy.POLICIES` and fails when a registered policy has no specification, so a new policy
cannot be added without one. The shared obligations in `_contract.md` come for free: the contract suite in
`tests/policy/test_policy_interface.py` is parametrised over `REGISTERED`, so a newly registered policy is
held to them from the moment it is added.

## What is not specified here

Only the five registered UAV policies and the contract they share. Three things next door are deliberately
left out, and their tests appear in the untagged list at the bottom of `TRACEABILITY.md` for that reason
rather than through neglect:

- **`SuperPolicy`** (`sim/policy/super_policy.py`, `tests/policy/test_super_policy.py`) — the fleet-wide
  composition layer that holds a policy per UAV and deconflicts the whole team afterwards. It is where the
  interesting safety properties live and is the obvious next thing to specify, as `POL-SUP-*`.
- **The MAPE-K components** (`sim/managing/`) — the analyzers and planners are policies of the managing
  system rather than of the agents. They have their own parametrised contract suite in
  `tests/managing/test_component_contract.py`, so the same scheme would fit them under `specs/managing/`.
- **A shared assumption register.** Assumptions are free text on the requirement that raises them. Once
  enough of them repeat across policies — `ACTIVATE_FIREFIGHTING`, `ACTIVATE_FUEL` and the relationship
  between `UAV_SPEED` and `UAV_OBSERVATION_RADIUS` already do — they are worth naming as `ASM-*` records
  and referencing, so that challenging one challenges every claim resting on it at once.

None of the three needs the scheme changed. Each needs specifications written.

## How this supports an assurance argument

The records here are structured so that an argument can be built over them directly, without a separate
modelling exercise. Nothing below requires GSN, but the mapping onto it is deliberate.

| Specification element | Role in the argument |
|-----------------------|----------------------|
| the statement blockquote | the claim being made about the policy |
| the prose below it | the justification for why that claim is the right one to make |
| the `**Assumptions:**` list | the context the claim holds in, and the first place to look for defeaters |
| `satisfied_by` | the artefact the claim is about |
| tests tagged `verifies`, and their results | the evidence offered for the claim |
| `TRACEABILITY.md` | the index tying evidence to claims, regenerated from the sources |
| `verified_by: none`, and the gap summary | the claims currently offered without evidence |

Only the top and bottom halves of that table are machine-checked. The claim is extracted and enforced to
be an obligation, and the links to artefact and evidence are resolved and enforced to exist; the
justification and the assumptions are prose that a reviewer reads. That split is deliberate — a tool can
tell you a claim has no evidence, and cannot tell you a justification is any good.

Two properties are what make this worth more than a hand-written table.

It is **generated, not asserted**. `TRACEABILITY.md` is derived from the specs and the test markers every
time it is produced, so it describes the repository as it actually is rather than as it was when someone
last updated the document.

It **fails loudly**. `tests/test_traceability.py` breaks the build when a requirement loses its
verification, when a marker names an ID that no longer exists, or when `satisfied_by` points at a symbol
that has been renamed away. An argument whose evidence links are checked by the same suite that checks
the code is an argument that can be trusted between reviews, which is the property a table maintained by
hand can never have.

What this does *not* establish is that the requirements are the right ones, or that the tests are strong
enough to support the claims they are attached to. Those are review judgements. The machinery here makes
them reviewable; it does not make them.
